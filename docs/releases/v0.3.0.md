# v0.3.0 release preparation

Status: prepared for review; not published. The Windows deployment must be built
and accepted from the final merged source before publication. This minor release
includes the GeMS, continuation, and recovery features merged since v0.2.0, as
well as the new output documentation. Dependency pins are unchanged.

## Draft release notes

Geo Map Exp Extractor v0.3.0 adds GeMS DMU staging, recoverable GUI extraction,
and a complete reference for output files and audit metadata.

Changes since v0.2.0:

- A 15-column GeMS DMU profile with a pinned GeoMaterial vocabulary, field
  validation, hierarchy guidance, and publication review instructions.
- Improved extraction prompts for layout, headings, source coverage, and
  profile-controlled text preservation and normalization.
- GUI extraction checkpoints, conservative recovery of complete rows from
  interrupted responses, cancellation, and explicitly requested continuation
  into a separate project folder.
- Local autosave/recovery of unsaved review work, with project identity and
  saved-revision checks.
- Repair of derived checkpoint exports even when no new rows were added.
- Expanded run-folder documentation and a searchable output reference covering
  JSON fields, request schemas, statuses, hashes, review events, cache, recovery,
  continuation, and audit limitations.

Existing run folders can be reopened with Load Project. Preserve an archive
before further review: opening a checkpoint-backed project can regenerate its
derived exports. Older projects without extraction checkpoints can still be
reviewed but cannot use checkpoint continuation. GeMS output remains a staging
table requiring geological, hierarchy, identifier, and database review.

The planned Windows asset is `GeoMapExpExtractor-Windows-v0.3.0.zip`. Once that
asset is built, validated, attached, and the release published, extract it into
a writable folder and double-click **Run Geo Map Exp Extractor.bat**. GitHub's
automatic source archives are not the ready-to-run Windows deployment.

The existing deployment approach uses private managed Python and locked
dependencies. First setup requires permitted HTTPS access; live extraction
requires an OpenAI API key. The GUI can open without a key.

## Packaging and publication handoff

The v0.2.0 release used the separate Python Deployment Builder in source mode.
This application repository has no GitHub Actions release workflow. Use a clean,
pinned builder checkout and its documented assess/plan/generate/validate/package
workflow; record its actual revision instead of assuming the previous builder
or runtime versions still apply.

1. Merge the release-preparation PR and record the exact resulting source commit.
   Build from a clean checkout of that commit with package/lock version `0.3.0`.
2. Validate the lock against project metadata using the release builder's pinned
   tooling. Generate a source deployment with bundled, verified uv and the
   established Windows certificate-store policy.
3. Check that the kit includes `README.md`, `docs/output_reference.md`,
   `docs/gems_dmu_review.md`, all selected profile YAML/notes and vocabulary CSVs,
   and both extraction and continuation prompt templates. Test the new README
   link in the application's Help window, including Back/Forward navigation.
4. Run static validation and isolated runtime validation, including dependency,
   launch, Diagnose, and Repair checks. Record managed Python/uv versions and
   outcomes. Re-run the application tests/lint against the final source as needed.
5. Perform GUI acceptance: open without an API key, inspect a dry run, reopen a
   copied project, edit/save/reload a table, verify recovery of unsaved review,
   and inspect/continue an interrupted checkpoint. Live continuation is a paid
   API operation; record explicitly whether it was tested. Confirm that the
   original project remains usable and that incomplete output is clearly marked.
6. Package twice and compare hashes to establish reproducibility. Validate the
   extracted ZIP. Capture manual GUI acceptance against that exact candidate.
7. Attach the ZIP, `GeoMapExpExtractor-Windows-v0.3.0.zip.sha256.txt`,
   `release-manifest.json`, and `SMOKE-TEST.txt`, matching the prior asset set.
   Replace draft validation language with actual results and provenance.
8. Create tag `v0.3.0` at the verified merged source commit and publish the release
   only after acceptance. Do not tag the preparation branch or publish an assetless
   Windows deployment release.
